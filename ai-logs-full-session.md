     1. Как я понял задание

     Бриф описывает не «страницу со списком поездов», а посадочную страницу под 
     органический
     трафик, которая обязана дожить до брони. Пять сигналов из брифа, каждый со
     своим техническим
     следствием:

     1. «Половина продаж — из поиска Google вида "Paris to Amsterdam trains"» —
     главный сигнал.
     Значит: HTML с результатами приходит с сервера, а не рисуется после
     гидратации; у каждого
     маршрута свой title/description; страница быстрая. Это диктует SSR как
     основу, а не как опцию.
     2. «Ссылками делятся в мессенджерах, получатель должен увидеть те же 
     параметры» — состояние
     поиска целиком живёт в URL. Никакого скрытого клиентского состояния,
     влияющего на выдачу.
     Это же требование даёт бесплатно: работающие «назад/вперёд», перезагрузку
     страницы, SSR.
     3. «Доступность мест должна быть точной. Если мест не хватило — понятное 
     сообщение и
     возможность вернуться к другим вариантам» — сценарий 409 это не край, а
     часть основного
     потока. Отсюда прямое следствие: оптимистичный UI при бронировании запрещён
     — он ровно
     то и делает, что показывает недостоверную доступность. Истина только в
     ответе сервера.
     4. «API медленный и иногда недоступен. Состояния загрузки и ошибок не 
     должны выглядеть
     поломкой» — скелетоны и обработка ошибок это функциональное требование с
     явной формулировкой
     в брифе, а не полировка в конце.
     5. «Сохранить поезд, сохранённые — наверху» + «аккаунтов и синхронизации 
     нет, планируются
     на следующий квартал» — бриф сам называет решение: локальное хранилище,
     осознанно временное.
     Проектировать под будущую замену на бэкенд, но не строить абстракцию под
     несуществующий API.

     Дополнительные факты, влияющие на код:

     - POST /bookings → 201 {id, trainId, seats, seatsLeft, status, createdAt} —
     возвращает
     свежий seatsLeft, им и обновляем UI без лишнего запроса.
     - 400 → {"error":"trainId is required and must reference an existing 
     train"},
     409 → {"error":"Not enough seats left on this train"}, 404 →
     {"error":"Train not found"}.
     Форма ошибки одинаковая — один парсер на все случаи.
     - seats: 0 возвращает 201 и бронирует 1 место (falsy-дефолт на бэкенде).
     Значит клиент
     обязан валидировать seats >= 1 сам, нельзя рассчитывать на отказ сервера.
     - /stations отдаёт не массив, а объект-словарь по слагу: {"berlin": {code, 
     name, country}, ...},
     11 немецких городов. Городов из брифа (Paris, Amsterdam) в API нет.
     - Неизвестные sortBy не роняют запрос, а игнорируются — валидируем на своей
     стороне.
     - Первый запрос после простоя ~1.7 с (cold start Render) — «медленный API»
     из брифа реален.

     Как закрываю отсутствие фильтра по цене

     Один запрос за весь датасет маршрута (?from&to&date&limit=1000, кэшируется

     сервере.

     упрощение. При

     4. Технологии

     Ядро

     - Next.js 15, App Router. Обязателен по заданию; App Router — потому что
     серверные компоненты
     дают SSR-HTML по умолчанию (требование 1), <Suspense> даёт стриминг и
     мгновенный скелетон
     при медленном API (требование 4), generateMetadata даёт метаданные под
     конкретный маршрут,
     а Server Actions закрывают бронирование без клиентского слоя запросов. На
     Pages Router каждый
     из этих пунктов пришлось бы собирать вручную.
     - TypeScript, strict. Обязателен.
     - Tailwind CSS v4. Mobile-first по своей природе, нулевой рантайм (важно
     для LCP, а скорость
     прямо названа в брифе), самый быстрый способ писать разметку за
     ограниченное время. CSS-in-JS
     плохо живёт с RSC, CSS Modules медленнее в написании.
     - shadcn/ui — минимальный набор (Select, Dialog, Button), скопированный в
     репозиторий.
     Это Radix: доступный Select с клавиатурной навигацией там, где писать его
     руками — заметная
     трата времени без продуктовой отдачи. Код остаётся нашим, vendor lock-in
     нет.
     - Zod. Парсинг searchParams в типизированный SearchQuery и валидация
     ответов API на
     границе. Прямо обслуживает «API может быть недоступен» — некорректный ответ
     становится
     обработанной ошибкой, а не падением рендера. Заодно делает контракт URL
     тестируемым.

     Данные и состояние

     - Чтение — нативный fetch в серверных компонентах с кэшем Next (next: { 
     revalidate }).
     - Мутация — Server Action + revalidatePath. Base URL API не уезжает в
     браузер, форма
     работает без JS, после успеха инвалидируется кэш выдачи. 409 возвращается
     как типизированный
     результат ({ ok: false, reason: 'not_enough_seats', seatsLeft }), а не как
     исключение —
     ветка восстановления получается обычным рендером, а не catch-блоком.
     - Состояние поиска — URL. Состояние сохранённых — localStorage через
     useSyncExternalStore (правильный getServerSnapshot снимает рассинхрон
     гидратации, который
     иначе неизбежен, и даёт синхронизацию между компонентами бесплатно, ~60
     строк).

     Осознанно не берём, и это часть аргументации:

     - TanStack Query — дублировал бы серверный кэш RSC. Клиентских перезапросов
     в этом объёме нет.
     - Redux / Zustand / Jotai — глобального клиентского состояния, кроме списка
     сохранённых, нет.
     Zustand с persist был бы разумной альтернативой, но useSyncExternalStore
     всё равно нужен
     ради гидратации, так что зависимость не окупается.
     - tRPC / GraphQL — один REST-API из пяти эндпоинтов, который нам не
     принадлежит.

     Качество

     - Vitest + React Testing Library + MSW. Vitest — нативные ESM/TS без
     babel-конфига. MSW важнее
     прочего: мокаем HTTP, а не свои модули, поэтому тесты проходят через
     настоящий код клиента,
     включая таймауты, ретраи и разбор ошибок. POST /reset никогда не дёргается 
     из тестов —
     общий стенд, тесты обязаны быть изолированными.
     - ESLint 9 flat config: next/core-web-vitals, @typescript-eslint с
     type-checked правилами,
     jsx-a11y. Политика --max-warnings=0, иначе «без ошибок ESLint» из
     определения шага
     превращается в накопление предупреждений. Prettier отдельно.
     - GitHub Actions: lint → typecheck → test → build. CI буквально кодирует
     определение
     готовности шага, а не полагается на дисциплину.
     - npm — «установить одной командой, запустить другой» без установки лишних
     инструментов
     ревьюером: npm ci, npm run dev.

     Порог покрытия

     100% строк и веток — только для src/domain и src/lib/api: там живёт вся
     логика, где ошибка
     стоит денег (цена, фильтрация, разбор URL, обработка кодов ответа). Для
     React-компонентов —
     тесты критических путей (ветка 409, пустая выдача, восстановление после
     ошибки, сохранение
     поезда), а не покрытие ради метрики.

     5. Пошаговый план

     Определение готовности каждого шага: работающий кусок функционала + тесты

     зелёный.
     Один шаг — один коммит.

     Шаг 0 — Каркас

     Next 15 + TS strict + Tailwind v4; ESLint flat + Prettier; Vitest + RTL +
     MSW + jest-dom;
     скрипты dev/build/start/lint/typecheck/test/test:coverage/verify; GitHub
     Actions; .env.example
     с TRAIN_API_BASE_URL; CLAUDE.md; заготовка README.
     Готово: npm ci && npm run verify зелёный, / отдаёт заглушку.

     Шаг 1 — Клиент API и типы предметной области

     src/lib/api/: Zod-схемы Train, Station, Booking; fetchJson с таймаутом
     через
     AbortController, ретраем с экспоненциальной задержкой только для
     идемпотентных GET и
     разбором {error}; типизированное объединение ошибок NotFound | Conflict | 
     Network | Timeout | InvalidResponse.
     Тесты (100%): 200 / 400 / 404 / 409 / 500 / таймаут / битый JSON / ответ не
     по схеме.

     Шаг 2 — Контракт поискового запроса

     src/domain/search-query.ts: parseSearchQuery(URLSearchParams) → SearchQuery
     и обратная
     сериализация. Детерминированный порядок параметров (одинаковая ссылка =
     одинаковая строка),
     дефолты, зажатие диапазонов (page >= 1, maxPrice >= 0, whitelist sortBy),
     некорректные
     значения отбрасываются, а не роняют страницу.
     Тесты (100%): round-trip, мусор в параметрах, пустая дата, канонический
     порядок.
     Это шаг, который технически обеспечивает требование «получатель ссылки
     видит те же параметры».

     Шаг 3 — Серверный конвейер выдачи

     src/domain/: чистые filterByMaxPrice, sortByPrice, paginate.
     src/lib/api/get-search-results.ts: запрос датасета маршрута с limit=1000 и
     revalidate,
     затем конвейер. Возвращает { items, total, page, totalPages }, где total —
     после фильтра
     по цене (иначе пагинация врёт).
     Тесты (100%): граница цены включительно, пустой результат, страница за
     пределами, стабильность
     сортировки при равных ценах; интеграционно через MSW.

     Шаг 4 — Страница /trains: форма и выдача

     Серверный компонент читает searchParams → шаг 2 → шаг 3. Форма: from/to из
     /stations
     (+swap), дата, бюджет, сортировка; отправка = навигация на новый URL.
     Карточка поезда, список,
     пагинация ссылками, пустое состояние с подсказкой ослабить фильтры.
     Mobile-first: одна колонка,
     фильтры в раскрывающейся панели на узких экранах.
     Тесты: серверный HTML содержит результаты (проверка требования 1); отправка
     формы даёт
     ожидаемый URL; отрисовка пустого состояния.

     Шаг 5 — Устойчивость

     loading.tsx + <Suspense> со скелетоном списка (форма видна сразу, ждёт
     только выдача);
     error.tsx с кнопкой повтора; баннер недоступности API; отдача последнего
     успешного кэша
     с честной пометкой, когда апстрим лежит.
     Тесты: MSW-сценарии 500 / таймаут / недоступность — каждый даёт осмысленный
     экран, а не пустоту.

     Шаг 6 — Страница поезда /trains/[id]

     SSR, короткий revalidate или no-store — актуальность мест здесь важнее
     кэша; 404 → notFound();
     кнопка возврата к выдаче с сохранением исходного запроса; generateMetadata.
     Тесты: рендер, 404, ссылка возврата сохраняет параметры.

     Шаг 7 — Бронирование и ветка «мест не хватило»

     Счётчик мест, зажатый в 1..seatsLeft (помним про баг с seats: 0). Server
     Action → POST /bookings.
     - 201: подтверждение, seatsLeft берём из ответа, revalidatePath на выдачу.
     - 409: заметное сообщение «мест больше нет», перезапрос поезда и показ
     актуального остатка,
     крупная кнопка возврата к другим вариантам с сохранённым запросом. Это ядро
     требования брифа.
     - 400 / сеть: различимые сообщения с возможностью повтора.
     Тесты: все четыре ветки; отдельный тест на то, что 0 мест не уходит в
     запрос.

     Шаг 8 — Сохранённые поезда

     Хранилище на useSyncExternalStore над localStorage: валидация схемой при
     чтении, устойчивость
     к битому JSON и переполнению квоты, лимит (20) с пояснением про будущую
     синхронизацию.
     Переключатель на карточке и на детальной; закреплённый блок «Сохранённые» 
     над списком
     результатов + бейдж на карточках в выдаче. Рендер после монтирования —
     гидратация без рассинхрона.
     Тесты (хранилище — полное покрытие): добавление/удаление, битые данные,
     отсутствие localStorage,
     лимит; компонентный тест на закрепление и на бейдж.

     Шаг 9 — SEO

     tickets»);

     с перелинковкой популярных маршрутов.

  Чистая логика в search-results.ts: filterByMaxPrice → sortTrains → paginate,
  собранные в buildSearchResults. Тонкая обёртка в get-search-results.ts: один
  кэшированный запрос за датасетом маршрута и делегирование в domain.

  Три решения, которые здесь важнее кода:

  1. Порядок фильтр → сортировка → пагинация несущий. Считать total до
  применения бюджета — значит обещать страницы, которые бюджет уже отсёк.
  Фильтровать только видимую страницу — показать 3 карточки из 20 при потолке
  €80. Оба варианта покрыты тестами именно как «так делать нельзя».
  2. Сортируем локально, sortBy API не используем. Пагинация локальная, значит и
  порядок должен решаться локально, иначе они разойдутся. В компараторе явный
  тай-брейк по дате → времени → id: живая проверка показала, что в berlin→munich
  четыре пары одинаковых цен (23, 31, 83, 99). Без полного порядка два запроса
  могли бы упорядочить их по-разному, и пользователь при листании увидел бы один
  поезд дважды, а другой потерял.
  3. Усечённый датасет бросает ошибку, а не фильтруется. Если API когда-нибудь
  вернёт меньше, чем заявил в total, мы молча показали бы неверный «самый
  дешёвый поезд» — отказ, который не заметит ни пользователь, ни ревьюер. Текст

  Три решения, которые важнее кода:

  1. Закреплённый блок, а не сортировка внутрь списка. Это тот пункт, где я
  спорил с брифом на этапе плана, и живая проверка его подтвердила: сохранённый
  поезд остаётся виден даже после перехода на совершенно другой маршрут.
  Всплытие внутри списка переставило бы только видимую страницу.
  2. Сохранённый поезд намеренно не помнит seatsLeft. Счётчик мест, замороженный
  в момент сохранения, — та же недостоверная доступность, которую мы выжигали в
  шаге 7. Карточка ведёт на страницу поезда, где число настоящее.
  3. Гарантия гидратации проверяется, а не предполагается. Панель прогоняется
  через renderToStaticMarkup с непустым списком и обязана отдать пустую строку.
  Если сервер когда-нибудь отрендерит список, которого не может знать, React
  выбросит всё дерево.

  Хранилище считается враждебным: не-JSON, не массив, записи старой схемы. Одна
  нечитаемая запись выпадает, не забирая с собой остальной шортлист; отказ
  записи по квоте всё равно обновляет список в памяти, так что сессия продолжает
  работать.

  Next-индикатор сразу показал 1 Issue, в серверном логе: Encountered two 
  children with the same key, ``.

  Причина. Форма поиска и Suspense-граница результатов обе ключевались строкой
  поиска, чтобы перемонтироваться при смене URL. На хабе /trains поиск пустой, и
  serializeSearchQuery(...) возвращает "" — оба соседних элемента получали
  key="". React не может их различить и вправе переиспользовать состояние не
  того элемента: практически это значит, что при переходе с хаба на маршрут
  введённые в форму значения могли уехать в чужой узел.

  Исправление. Ключи разведены префиксами: form:${searchKey} и
  results:${searchKey}. page.tsx

  Дефект 2 — пагинация загоняла в тупик

  Причина. Previous всегда вёл на page - 1. Со страницы 99 из 2 это страница 98
  — тоже пустая, и так 97 раз. Ссылка «на первую страницу» в пустом состоянии
  была, но рядом стоял контрол, приглашающий кликать в никуда.

  Исправление. Цель Previous зажата последней реальной страницей: Math.min(page 
  - 1, totalPages). Со страницы 99 из 2 теперь ведёт на 2. pagination.tsx,
  добавлен тест.

  Шероховатость — заголовок над пустой секцией

  У распроданного поезда над блоком без формы стоял заголовок «Book seats».
  Читается как не отрисовавшийся контрол, а не как полный поезд. Теперь при
  нулевой доступности заголовок — «Fully booked».
